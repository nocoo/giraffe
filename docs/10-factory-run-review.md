# 10 — 持久刷新审查与验证

2026-09-16，Grok CLI 与 Pi CLI 在本项目工作目录内独立审查设计、数据路径、并发、迁移、性能与 UX；审查采用只读源码包，不传生产凭据或私有事件。

## 有效意见与处理

- **存储增长及引用安全**：0002 保存 publication 引用清单并有界清理；0003 覆盖运行/检查点、仓库状态与版本、资源、所有 factory 快照及引用的字节计量。256 MB 预算保留 2 MB 控制空间，不以资源流字节冒充总工厂数据。
- **贡献与混合窗口**：贡献来源单独保存；失败保留旧日历并标本次 unavailable。日历/账本按各仓库窗口并集计算每日覆盖，未知零与观测下界分别表示，不把混合数据当统一 90 天趋势。
- **并发及中断**：启动和冷却同事务；claim 后 fenced 保存当前步骤再请求 GitHub；凭据暂停和网络失败分开计数；取消/暂停已开始仓库同事务保留冷却。
- **计划语义**：成员与优先级分别使用 repos/order，filter 由服务端解析，selection 保存条件和最终顺序；selected 的优先级同样在服务端生效。
- **覆盖退化**：complete 或有记录的 limited 数据不会被更弱的新观测覆盖。
- **内存边界**：工厂响应读取时限 4 MB，超限中断读取；其他原有 API 单独限 20 MB。
- **迁移兼容**：实际备份副本重复应用全部迁移，开启外键，验证唯一活动索引、条件写入、计量、引用写入及探针回滚；旧表逐行摘要保持一致。
- **快照物理分页**：Pi 最终提出同一逻辑快照从两页变为一页时旧 #2 残留的问题。现已在同一 fenced batch 删除旧物理页再插入完整新页集，并有回归测试。

Grok closing review 对核心六项修正给出 Ready；Pi closing review 除物理分页项外确认实现与约定一致。关于“发布读取所有历史版本”的早期意见不成立：查询一直以 `s.version=v.version` 限定当前指针，多版本回归测试已证明不会读入更新但未发布的历史版本。

另补充租约临界回归：若准备某条写入时租约有效、最终提交时已过期，单靠各语句不同时间的条件可能出现部分写入。因此保存事务先断言所有已准备 fence 的最大时间仍有效，失败会回滚整批；随后才执行带同一 token/version 的写入和最终 CAS。测试覆盖过期、接管、暂停及调用时钟回拨。

## 验证范围

L1 覆盖冻结计划、范围/顺序、并发启动与控制、冷却、租约恢复、分页幂等、部分失败保旧、总字节预算、引用保留/清理、贡献来源、混合日覆盖、有界响应、API 与串行轮询。L2 使用隔离的真实 Worker/D1/Queue；浏览器 smoke 创建单仓库 run，重载核验同一 run/固定步骤，完成后验证快照保留，并检查桌面与 390px 界面。所有夹具与生产资源隔离。

生产发布和 smoke 的最终结果以发布执行记录为准；此文不把本地浏览器验证冒充生产验证。
